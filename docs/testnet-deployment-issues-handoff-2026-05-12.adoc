== Purpose

This document is a handoff for continuing the Stellar testnet deployment and transaction validation work.

The immediate objective is not to deploy every vault at once. The required flow is:

. Deploy and test `Beta` first.
. Fix every Beta transaction failure.
. Only after Beta succeeds end-to-end, deploy and test `Alpha` and `Gamma`.
. `Gamma` must use only the Blend lending strategy.

The latest testnet run showed that many earlier problems were fixed, but two Beta blockers remain.

== Important Design Constraints

The following constraints must be preserved while fixing the remaining issues.

* Vault withdrawals must keep the current accounting model: withdraw proportionally from all tracked idle assets and all tracked strategy positions.
* Do not change withdraw to "idle USDC first".
* Do not use stale cached NAV, LP value, or strategy value as authoritative accounting.
* Prices and AMM reserves change over time, so NAV must be based on fresh values in the current transaction.
* It is acceptable and recommended to cache/index immutable metadata and bounded quantities, for example token ordering, strategy position indexes, tracked assets, and LP balances.
* Share tokens are non-transferable by default.
* Cooldown is enabled as a hard control while shares are non-transferable.
* PnL tracking is accurate only in the default non-transferable-share mode.
* If share transferability is enabled in the future, cooldown is no longer a hard security control and PnL becomes informational/approximate.

== Issues Already Fixed During Testnet Work

=== Nested Vault Authorization

Earlier testnet runs failed with `Error(Auth, InvalidAction)`.

Root cause:

* Strategy operations tried to pull tokens from the vault using nested authorization.
* On Soroban, the vault should not rely on a strategy pulling funds from it using nested `authorize_as_current_contract` patterns.

Fix already implemented:

* `vault.execute_op` pre-funds the strategy with required input assets.
* Strategies consume assets already received from the vault.
* Strategy functions no longer pull input tokens from the vault.

Main files:

* `contracts/vault/src/lib.rs`
* `contracts/strategies/soroswap_lp/src/lib.rs`

=== Soroswap Mock Pricing

Earlier testnet runs failed TVL guard after swap.

Root cause:

* The mock Soroswap router returned 1:1 output amounts.
* The oracle priced XLM at `0.17` USDC, so a 1:1 USDC-to-XLM mock swap looked like a large value loss.

Fix already implemented:

* `contracts/mock_soroswap_router/src/lib.rs` now accepts `price0` and `price1`.
* `swap_exact_tokens_for_tokens` computes price-aware output:
+
[source,text]
----
amount_out = amount_in * price_in / price_out
----

Deployment script update:

* `scripts/deploy_testnet_protocol_environment.sh` deploys the mock router with `--price0` and `--price1`.

=== Soroswap Add Liquidity Budget

Earlier Beta runs failed on manager `add_liquidity` with `Error(Budget, ExceededLimit)`.

Root cause:

* Add-liquidity used longer approval expiry and explicit zero-approval revoke after the router call.
* The transaction also performed vault pre/post guard accounting.

Fix already implemented:

* `SoroswapLpStrategy.add_liquidity` uses same-ledger approval:
+
[source,rust]
----
let expiry = env.ledger().sequence();
----

* Explicit zero-revoke was removed for add-liquidity and swap.
* The router return `(amount_a_used, amount_b_used, lp_received)` is used by the vault to avoid an immediate deep post-operation LP revaluation when possible.

Result:

* In latest run, manager Soroswap add liquidity succeeded.

== Remaining Issue 1: Soroswap Remove Liquidity Budget Failure

Latest failure:

[source,text]
----
Manager remove Soroswap LP liquidity:
failed: transaction simulation failed: HostError: Error(Budget, ExceededLimit)
----

Current likely cause:

* `SoroswapLpStrategy.remove_liquidity` still uses `expiry = env.ledger().sequence() + 100`.
* It still performs an explicit zero-approval revoke after the router call.
* Unlike `add_liquidity`, it currently returns `()` instead of returning the actual `(amount_a, amount_b)` received from the router.
* The vault may need to do a deep post-operation strategy valuation to enforce/update value guards.

Relevant file:

* `contracts/strategies/soroswap_lp/src/lib.rs`

Current function:

[source,rust]
----
pub fn remove_liquidity(env: Env, vault: Address, lp_amount: i128, min_a: i128, min_b: i128)
----

Recommended fix:

. Change remove-liquidity approval to same-ledger approval:
+
[source,rust]
----
let expiry = env.ledger().sequence();
----

. Remove the explicit zero-approval revoke, matching the already-fixed `add_liquidity` and `swap` approach.
. Change the strategy function to return the actual router output:
+
[source,rust]
----
pub fn remove_liquidity(...) -> (i128, i128)
----

. In `vault.execute_op`, when `fn_name == "remove_liquidity"` and the returned value is `(amount_a, amount_b)`, use those returned underlying amounts plus fresh oracle prices to compute the local post-operation value impact.
. Keep the TVL/value guard semantics. Do not bypass the guard. The optimization should reduce redundant deep valuation, not remove security checks.

Important:

* The returned amounts are current-transaction quantities from the router.
* The vault must still price them with fresh oracle/AssetHandler prices.
* This does not introduce stale accounting.

== Remaining Issue 2: Phase 3 User Deposit Budget Failure

Latest failure:

[source,text]
----
Phase 3 user deposit after manager actions:
failed: transaction simulation failed: HostError: Error(Budget, ExceededLimit)
----

Why this happens:

* A deposit calls fee collection/accounting.
* Fee collection needs current NAV.
* Current NAV values:
** tracked idle assets,
** Blend position,
** Soroswap LP position,
** any other non-zero strategy positions.
* The Soroswap LP valuation currently performs several nested calls:
** strategy storage reads,
** factory `get_asset_handler`,
** pair `get_reserves`,
** pair `total_supply`,
** pair `token0`,
** AssetHandler `get_price(asset_a)`,
** AssetHandler `get_price(asset_b)`,
** underlying oracle calls.

This is correct logically, but too deep for Soroban when combined with the rest of the deposit transaction.

Relevant files:

* `contracts/vault/src/lib.rs`
* `contracts/strategies/soroswap_lp/src/lib.rs`
* `contracts/strategies/soroswap_lp/src/storage.rs`
* `contracts/asset_handler/src/lib.rs`
* `contracts/oracle/src/lib.rs`

Recommended fix:

. Keep NAV live and fresh.
. Make LP valuation quantity-based and bounded.
. Add a cheap Soroswap LP strategy method that returns current underlying quantities:
+
[source,rust]
----
get_underlying_balances(vault) -> (i128, i128)
----

. The strategy should compute:
+
[source,text]
----
amount_a = lp_balance * reserve_a / total_lp
amount_b = lp_balance * reserve_b / total_lp
----

. Cache immutable token ordering at initialization to avoid calling `pair.token0()` on every valuation:
+
[source,text]
----
Token0IsAssetA: bool
----

. Let the vault price the returned quantities using fresh prices from AssetHandler/Oracle.
. Prefer batch price reads where possible.

The oracle already has batch pricing:

[source,rust]
----
oracle.get_prices(assets: Vec<Address>) -> Map<Address, i128>
----

AssetHandler currently exposes single-asset `get_price`. A useful improvement is to add an AssetHandler batch method:

[source,rust]
----
get_prices(assets: Vec<Address>) -> Map<Address, i128>
----

This method should preserve AssetHandler semantics:

* asset must be registered,
* use asset-specific oracle if configured,
* otherwise use primary oracle,
* fallback oracle behavior must remain the same,
* reject zero or invalid prices.

== Why Increasing Budget Alone Is Not The Fix

Manual testing with higher Stellar CLI instruction leeway was attempted and did not resolve the remaining failures.

The issue is not simply that the CLI simulation needs a larger estimate. The composed call graph is too expensive:

[source,text]
----
vault user action
  -> fee/NAV accounting
  -> tracked idle asset valuation
  -> active strategy valuation
  -> LP reserve decomposition
  -> pair/router calls
  -> AssetHandler calls
  -> oracle calls
  -> token balance/supply calls
----

On EVM, this would often be treated as a gas-cost problem. On Soroban, there are stricter per-transaction execution and resource limits. The protocol must bound the amount of work per transaction.

== Comparison With dHEDGE V2 Design

dHEDGE V2 avoids this class of issue because it uses an asset/guard design where each asset type has a bounded guard and the pool does not deeply execute every integration path during every user action.

The Stellar version should follow the same principle:

[source,text]
----
Vault:
  owns NAV, fees, shares, withdrawals, and accounting policy

Strategy:
  executes protocol actions
  exposes cheap current position quantities

AssetHandler/Oracle:
  provides fresh prices, ideally batched
----

Do not cache stale values. Cache metadata and bounded position indexes.

== Short Diagnosis

The protocol logic is moving in the right direction, but the remaining Beta failures show that the current valuation path is still too expensive for Soroban when live LP positions are present.

The correct fix is a dHEDGE-style bounded accounting design:

* cache/index metadata and positions,
* expose current strategy quantities cheaply,
* price those quantities freshly,
* batch price reads where possible,
* preserve proportional withdrawals and live NAV.
